# Spike 014: protected TEST personal binding and signed intents

Historical checkpoint: the current mandatory retained-checkpoint initialization
and restore procedure is in [Spike 015](../015-retained-binding-checkpoint/README.md)
and [nca/README.md](../../../nca/README.md). Original Spike 014 backups alone must
not be treated as current authorization or bootstrapped into a new checkpoint.

Baseline local `main`: `1c954bf247cafe5c63a4ef2da538ce57b24eb1cb`.
Continue the approved key-protection and dedicated registration/replacement step.
No HTTP login, corporate representation, wallet, grant, payment, push or devnet.

## Plan and acceptance

1. Explicitly initialize a private local TEST mapping key and SQLite binding
   metadata. Existing state cannot be overwritten; missing/changed/insecure keys
   must fail closed, not generate another person ID. Provide a protected consistent
   local backup and prove restore/restart keep the binding.
2. Store exact session-bound expiring enrolment/replacement intents. Only verified
   fresh TEST CMS over those bytes can update a personal binding. Organization
   credentials are ineligible even for the same IIN; source, mapping key, target,
   candidate certificate and expected epoch remain bound. Replace atomically with
   receipt/nonce consumption, retire the old credential and refuse reuse within
   the current registry. A restored older snapshot is not global anti-rollback.
3. Test replay, parallel/stale requests, changed bytes, expired/unavailable status,
   corporate/foreign/retired credentials, transaction failure and key loss/change.
   Prove genuine SDK personal enrolment and negative replacement cases. Positive
   same-profile renewal remains a fixture gap; synthetic callbacks are labelled.

Reuse Node crypto/filesystem/SQLite and `sdk.verifyIdentity`; no dependencies or
public endpoints. The existing OwnerStore requires a wallet, so do not invent one:
these are separate **personal binding records**, not Solana owner/grant records.
Current browser probe receipts cannot be upgraded into enrolment or login.

## Implemented local boundary

`nca/personal-bindings.mjs` adds operator-only initialization, protected key/database
checks, canonical five-minute intents, SDK-backed personal evidence and atomic
binding/epoch/retirement/receipt updates. No mapping key is generated by opening
a store or submitting an operation. The key is 32 random bytes in an owner-only
file; its domain-separated fingerprint is pinned in SQLite and each intent.
Key/file/metadata loss, change, symlink or permission failure refuses. The database
inode is pinned while the store is open. Incomplete provisioning is retained for
operator recovery rather than overwritten. Key buffers are cleared on completion;
this is not an encrypted vault or a guarantee of complete JVM/OS memory erasure.

- Enrollment accepts only exact fresh eligible **personal TEST** CMS. A new
  certificate on an existing person requires the separate replacement action.
- Replacement binds target ID, current certificate, candidate certificate, epoch,
  nonce, session, key fingerprint and TEST OCSP source. A foreign person, org
  context, stale epoch, mismatched candidate or retired certificate refuses.
- Receipt, binding update, epoch increment and retirement share `BEGIN IMMEDIATE`.
  A write error rolls all of them back. Identical retries return historical
  `test_personal_binding_only` receipts, not fresh authorization. Other CMS on a
  consumed intent conflicts. Concurrent stale replacements cannot both win.
  A domain-separated HMAC binds stored history to its exact intent/session/CMS
  hash and receipt; changed bytes, hashes or receipt JSON refuse on replay.
- Only hashes of CMS are persisted. There are no raw IIN/BIN, certificate names,
  private signing containers, wallet addresses or corporate grants in this store.
- `backupTo` stages a private key/database pair using SQLite online backup, checks
  metadata and `quick_check`, syncs files/directories and publishes by one rename
  under a trusted parent. Existing targets refuse; a failed unpublished copy removes
  only its owned temporary staging directory, permitting retry. Restarts and a current
  backup preserve the binding ID, opaque person ID, epoch and retired credentials.
  The result explicitly reports `published` and `durability`; a final parent-sync
  failure reports `parent_sync_unconfirmed`, not an unpublished retry failure.

parallel and stale requests, source/shape/key tampering, certificate/purpose/status
refusals, expiry during verification and at commit, missing/replaced/insecure keys,
database replacement, receipt-write rollback/retry, private backup and restart,
authenticated history mutation, failed/concurrent backup and final commit expiry.
Their verifier callbacks are **policy/storage doubles**, not genuine NCA proof.
Positive same-person personal renewal and retired-certificate reuse are modelled

organization context. A signing employee also refuses personal enrollment. None
of those negatives updates the personal binding. There is no eligible pair of
different, currently valid personal certificates in this bundle for positive
renewal acceptance.

Full stable suite: 112 Node + 7 offline Solana cases; all four SDK runs pass

## Limits and next gate

**PARTIAL, internal TEST metadata only.** No HTTP account, login/access check,
corporate policy, OwnerStore mapping, business grant, actual wallet or payment
is enabled. The previous browser signature receipt remains signature-only.

Local Unix owner/mode checks assume a trusted OS user and operator-controlled
directory. They do not defend against that OS user, privileged tampering, arbitrary
ACL inheritance or disk theft. Receipt MACs detect database-only history changes,
not whole-registry tampering or valid older snapshots; this is not a rollback-proof ledger.
Backups include the private mapping key and must receive the same protection.
An older backup restores older epochs and retirement data: a regression explicitly
demonstrates that limitation. Do not activate authorization from a restored snapshot
until a separate reviewed recovery/anti-rollback policy reconciles live state.
Atomic publication protects complete pairs against competing backups from this
method; it is not a portable no-clobber primitive against a separate same-OS-user
process creating an empty destination in the final rename window. Nonempty
destinations cannot be replaced. The trusted-parent/cooperative-operator assumption
and final parent-sync error branch need separate filesystem fault acceptance before
production custody; power-loss durability has not been established.

Next: review key custody/recovery and the HTTP session/CSRF/rate/storage boundaries,
then expose a separately labelled personal TEST enrollment UI and obtain an eligible
same-profile renewal pair. Corporate enrollment remains closed until a verified
powers source exists. Wallet creation requires its own approved, exact signed
operation and must not be inferred from enrollment. Official rules/SDK provenance
and a full independent NCA/authorization review remain open.

## Focused review

A separate read-only storage/policy review identified missing global snapshot
anti-rollback (P1), incomplete backup publication/retry (P2), and unchecked stored
history (P2). The latter two led to the staging/publication and receipt-MAC fixes
and regressions above. The P1 is **still open** and blocks authorization use;
the older-snapshot regression makes this explicit. This focused review is not a
complete NCA/HTTP/production security acceptance and is not a Claude review.
Follow-up review confirmed those fixes and found an expiry-column race during
verification; commit now requires the exact original expiry and MACs the checked
current row. The deferred-verifier regression also changes only that column.
Post-publication sync ambiguity now has an explicit result; adversarial empty-dir
publication races remain outside the trusted operator boundary above.
