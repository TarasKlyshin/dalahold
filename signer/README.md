# DalaHold signer — веха 1: офлайн-граница подписанта

**Статус:** локальная офлайн-проверка контракта и границы процесса. Здесь нет Solana-ключа, кодирования транзакции, RPC, devnet и сети. Отправка — симуляция: подписант фиксирует детерминированный фиктивный `tx_id` вида `sim_<hex>` и передаёт его колбэку. **Это не платёж, не escrow и не подтверждение в сети.** ЭЦП НУЦ РК подписант не проверяет — это зона эмитента разрешений (Codex).

Оператор подписанта — доверенная сторона: схема кастодиальная, а не trustless-кошелёк. Подписант полностью доверяет ключу политики. Кто владеет этим ключом, тот распоряжается тестовым кошельком в пределах лимитов ниже.

## Файлы и запуск

- `signer.mjs` — ядро, loopback HTTP и CLI; только стандартная библиотека Node.
- `signer.test.mjs` — офлайн-тесты: HTTP на `127.0.0.1` и перезапуск дочернего процесса.
- Нужен Node ≥ 22.13: используется `node:sqlite`, при загрузке он печатает `ExperimentalWarning`. Зависимостей нет, `npm install` не нужен.

```sh
node --test signer/signer.test.mjs
DALAHOLD_SIGNER_DIR=/path/outside/repo node signer/signer.mjs   # ручной запуск
```

`$DALAHOLD_SIGNER_DIR/config.json`:

```json
{
  "policy_public_key": "<base64url сырого 32-байтного публичного ключа Ed25519>",
  "wallets": { "<owner_id UUID>": "<base58-адрес кошелька>" },
  "port": 8787
}
```

- `policy_public_key` — только локально сгенерированный **тестовый** ключ политики (поле `x` его JWK). Доверенный ключ подписант берёт только из этого файла. Ключ, присланный в запросе, не принимается: лишнее поле в конверте или payload даёт `400`. Приватная половина остаётся у эмитента, вне Git. Публичный ключ из вектора ниже CLI отвергает.
- `wallets` — локальная фикстура «владелец → адрес» вместо keystore. Создания кошельков и маршрута `/wallets` в этой вехе нет.
- `port` необязателен: 0 означает случайный. Адрес всегда `127.0.0.1`. CLI пишет в stdout JSON-строки `{"event":"listening",…}` и `{"event":"simulated_send","grant_id":…,"tx_id":…}`.
- `signer.sqlite` (WAL, `synchronous=FULL`) создаётся с umask 077. Эксклюзивная блокировка SQLite не даёт запустить второй процесс на тот же каталог.
- В библиотечном режиме `new Signer({ dbPath, policyPublicKey, wallets, send })` принимает колбэк `send(tx)`. Он получает `{tx_id, grant_id, order_hash, cluster, program_id, wallet_address, recipient, amount_lamports}`. Успешное завершение означает «принято», исключение — «исход неизвестен».

Тестовый ключ политики на стороне эмитента:

```js
const { publicKey, privateKey } = crypto.generateKeyPairSync('ed25519');
publicKey.export({ format: 'jwk' }).x;               // → policy_public_key
privateKey.export({ type: 'pkcs8', format: 'pem' }); // хранить вне репозитория (*.pem в .gitignore)
```

## HTTP-граница

Есть только `POST /transfers` и `POST /epochs`. Любой другой метод, путь, завершающий `/` или query-строка дают `404`. Запрос должен иметь `Content-Type: application/json`, `Host: 127.0.0.1:<port>` или `localhost:<port>` и тело не больше 16 KiB. Тело содержит ровно два поля:

```json
{"payload":"<base64url байтов payload>","sig":"<base64url 64-байтной подписи>"}
```

base64url — по RFC 4648 §5, без `=` и пробелов. Любые другие поля (`transaction`, `message`, ключи и т. п.) дают `400 bad_envelope`. Готовые байты транзакции, сообщения или «подпиши это» подписант не принимает вообще.

## Контракт подписи (для эмитента)

1. `payload` — каноничный JSON в UTF-8 по правилам ниже.
2. Подписываемое сообщение — `DALAHOLD-SIGNER-V1\n` ‖ `payload`. Префикс занимает 19 байт ASCII, hex `44414c41484f4c442d5349474e45522d56310a`. Он разделяет домены: подпись тем же ключом над другим документом здесь не пройдёт.
3. `sig` — чистый Ed25519 (RFC 8032, не ph/ctx) над этим сообщением, 64 байта. В Node: `crypto.sign(null, message, policyPrivateKey)`.
4. Подписант сначала проверяет подпись над **сырыми** байтами ключом из своего конфига. Разбирает JSON он только после этого. Затем он требует, чтобы payload был единственной каноничной записью значения. Лишние пробелы, другой порядок, дубли ключей, `1.0` или `1e0`, `\u`-экранирование дают `400 payload_not_canonical`. «Похожий JSON» заново не сериализуется.

Правила каноничного JSON:
- без BOM и пробелов;
- ключи — ровно из таблицы, каждый один раз, в указанном порядке;
- целые — JSON-числа (safe integer) в десятичной записи, без знака, дроби и экспоненты;
- строки — обычные JSON-строки: все допустимые значения в ASCII, экранирование не возникает.

В JS это `JSON.stringify(value, FIELD_ORDER)`. В Python — `json.dumps({k: value[k] for k in FIELD_ORDER}, separators=(',', ':'))`.

### `test_transfer` → `POST /transfers`

| # | поле | тип | правило |
|---|---|---|---|
| 1 | `v` | число | `1` |
| 2 | `kind` | строка | `"test_transfer"` |
| 3 | `grant_id` | строка | UUID в нижнем регистре, новый для каждого разрешения |
| 4 | `owner_id` | строка | UUID в нижнем регистре: устойчивый ID владельца, не ИИН/БИН; должен быть в `wallets` |
| 5 | `auth_epoch` | число | ≥ 0, **равен** текущей эпохе владельца у подписанта |
| 6 | `cluster` | строка | `"devnet"` |
| 7 | `expires_at` | число | мс Unix UTC; `now < expires_at ≤ now + 300000` по часам подписанта |
| 8 | `order_hash` | строка | 64 hex в нижнем регистре: SHA-256 точных байтов ЭЦП-распоряжения, в которых есть случайный nonce; одно разрешение на одно распоряжение |
| 9 | `wallet_address` | строка | base58, 32 байта; совпадает с `wallets[owner_id]` |
| 10 | `program_id` | строка | `"11111111111111111111111111111111"` (System Program) |
| 11 | `asset` | строка | `"SOL"`; сумма в lamports |
| 12 | `recipient` | строка | base58, 32 байта |
| 13 | `amount_lamports` | строка | десятичная запись без ведущих нулей, от `1` до `1000000` |
| 14 | `max_fee_lamports` | строка | десятичная запись, не меньше `5000`. Модель комиссии: 1 подпись × 5000, без priority fee |

### `epoch` → `POST /epochs`

`{"v":1,"kind":"epoch","owner_id":"<UUID из wallets>","auth_epoch":<целое ≥ 1>}` — поля именно в этом порядке, подпись та же. Эпоха у подписанта только растёт. Уведомление применяется, если `auth_epoch` больше текущей (`applied: true`); иначе ничего не меняется (`applied: false`). Поэтому повторное или запоздавшее уведомление безвредно и срок действия ему не нужен. Пока уведомлений не было, владелец на эпохе 0. Ответ `200`: `{"owner_id":…,"auth_epoch":<текущая>,"applied":…}`.

## Проверки, ответы и коды ошибок

Порядок: соединение (loopback, `Host`, маршрут, тип, размер) → конверт → подпись → структура payload → идемпотентность → политика → подготовка и симулированная отправка. Ошибка возвращается как `{"error":"<код>"}`. Для записи в статусе `cancelled` (`403`) или `prepared` (`502 send_failed`) к ней добавляются поля записи.

Успех, `200`:

```json
{"grant_id":"…","order_hash":"…","status":"submitted","tx_id":"sim_<hex sha256(payload)>","send_attempts":1,"simulated":true,"replayed":false}
```

| HTTP | коды |
|---|---|
| 400 | `bad_envelope`, `payload_not_json`, `payload_fields` (не тот набор полей, в том числе документ другого вида на этом маршруте), `payload_kind` (`v` или `kind`), `payload_not_canonical`, `payload_invalid` (тип или формат поля) |
| 403 | `bad_signature` — изменён хоть один байт, подписано чужим ключом или без префикса; `loopback_only`, `bad_host`; политика: `cluster_not_allowed`, `program_not_allowed`, `asset_not_allowed`, `amount_over_cap`, `fee_cap_too_low`, `unknown_owner`, `wallet_not_bound`, `grant_expired`, `grant_ttl_too_long`, `stale_epoch`, `epoch_ahead` |
| 404 / 413 / 415 | `not_found` / `body_too_large` / `unsupported_media_type` |
| 409 | `grant_conflict` — тот же `grant_id` с другими байтами; `order_already_granted` — у этого `order_hash` уже есть другое разрешение |
| 502 | `send_failed` — симулированная отправка не подтвердилась; `status: "prepared"`, `tx_id` уже зафиксирован |

## Идемпотентность, статусы и повтор

- `tx_id` — это `sim_` плюс hex SHA-256 байтов payload. Он записывается в хранилище **до** отправки. В реальной вехе на этом месте будет подпись транзакции, собранной один раз.
- Статусы:
  - `prepared` — разрешение принято, отправка не подтверждена;
  - `submitted` — колбэк симуляции принял `tx_id`; это **не** подтверждение в сети;
  - `cancelled` — это разрешение больше никогда не будет отправлено; причина в `error`, ответ `403`.
- Повтор того же конверта возвращает сохранённый результат с `replayed: true` без новой отправки. Для `submitted` это верно и после истечения срока или ротации: повтор лишь читает результат, а не исполняет заново. Параллельные дубли присоединяются к уже идущей отправке, поэтому из 20 одновременных запросов получается ровно одна отправка.
- После `502` повторяйте **тот же** конверт. Подписант заново проверит политику: эпоху, срок, привязку кошелька.
  - Если проверка прошла, он повторно отправит тот же `tx_id`, ничего не подписывая заново.
  - Если эпоха сменилась или срок истёк, запись навсегда становится `cancelled` (`stale_epoch` / `grant_expired`).
  - Отправку, начатую до ротации, отозвать нельзя. При `send_attempts > 0` её исход неизвестен; в реальной версии здесь нужна сверка с сетью.
- В хранилище лежат разрешения, эпохи и подписанные конверты для аудита. Секретов там нет. Состояние переживает перезапуск и `SIGKILL`; это проверено тестом с дочерним процессом.
- Если `signer.sqlite` потерян, пропадает защита от replay для неистёкших разрешений, а эпохи сбрасываются в 0. Каталог нужно восстановить. Если это невозможно, до приёма разрешений подождите больше 5 минут (максимальный срок разрешения) и заново отправьте актуальные `/epochs`.

## Обязанности эмитента (Codex)

1. Выпускать разрешение только после проверки ЭЦП-распоряжения, сертификата и полномочий. Подписант всего этого не видит. До получения SDK НУЦ этот шаг — явно помеченный мок или fail-closed.
2. Одно `order_hash` — одно разрешение. Повтор после сбоя — это те же байты конверта, а не новое разрешение.
3. `expires_at` не дальше 5 минут вперёд; часы эмитента и подписанта синхронизированы.
4. При ротации отправить `/epochs` с новой эпохой **до** коммита rebind в БД. Если коммит упадёт, подписант будет отвечать `stale_epoch`, пока rebind не повторят, — система закрывается, а не открывается.
5. `502 send_failed` означает «исход неизвестен, ожидание» — это ни успех, ни отказ.
6. Тестовый ключ политики не ключ НУЦ и хранится вне Git.

## Что проверено и чего эта веха не доказывает

Тесты закрывают только сторону подписанта в строках приёмки `TECHNICAL_PROTOTYPE.md`, и только в пределах симуляции. Это replay и параллельные запросы, подмена полей **разрешения**, прямой обход, поддельное или использованное разрешение, смена эпохи между выдачей и исполнением. Ни один отрицательный случай не вызывает `send`. Подмену полей самого ЭЦП-распоряжения должен ловить верификатор эмитента.

Не доказано:
- ЭЦП НУЦ РК, сертификаты, OCSP/CRL и корпоративные полномочия: всё это вне подписанта и не интегрировано.
- Реальный Solana-ключ, сборка и подпись транзакции, RPC, devnet, подтверждение, переход в `expired` по blockhash. `submitted` значит лишь, что симуляция приняла фиктивный ID. Таймаута отправки нет: зависший колбэк держит запрос. Реальному RPC понадобятся таймауты и сверка статуса.
- Изоляция на уровне ОС и сервисная аутентификация сверх loopback. Любой локальный процесс может прислать конверт, но без ключа политики ничего не исполнит.
- Суммарный лимит: лимиты действуют на одно разрешение. Хранение ключа политики — ответственность эмитента.
- Работа нескольких экземпляров: на каталог данных один процесс, второй не стартует. Проверка `remoteAddress` страхует на случай, если сервер поднимут не на loopback; тестами она не покрыта.
