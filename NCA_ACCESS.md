# НУЦ РК: доступ для технического прототипа

Статус на 30.09.2026: SDK 2.0 и комплектные тестовые ключи скачаны. [Локальный стенд](nca/README.md) реализует страницу NCALayer, API точных одноразовых распоряжений и Java-проверку CMS. В отдельном явном TEST OCSP-режиме пройдены SDK- и ручной браузерный сценарии «точные байты → NCALayer/CMS → строгая проверка ответа официального TEST OCSP → одноразовая HTTP-квитанция», затем повтор с той же сохранённой квитанцией без новой проверки статуса. Принятый сертификат совпадает с комплектным профилем «Сотрудник с правом подписи»; это не проверка корпоративных полномочий. **CRL-режим остаётся закрытым:** base CRL №166 меньше требуемого delta BaseCRLNumber №167. Автоматического перехода на OCSP нет. `authority/`, устойчивая идентичность, роли сделки, полномочия и кошелёк ещё не связаны; квитанция имеет только `scope: test_signature_only`.

Утилита OCSP SDK не устанавливает доверие к ответчику, соответствие CertID и свежесть; она не используется для приёмки. [Spike 012](.planning/spikes/012-strict-test-ocsp/README.md) реализует отдельную проверку доверенного ответчика, подписи, назначения, CertID, 32-байтового nonce и времени. Пройдены 47 синтетических/транспортных проверок и обязательные отрицательные проверки настоящих комплектных сертификатов: текущий `Физическое лицо/revoked` отклонён по проверенному TEST OCSP `revoked`, а `Казначейство клиент/valid` — до OCSP из-за отсутствия требуемого стендом назначения подписи. В обоих случаях квитанции и погашения запроса нет. 88 Node + 7 offline Solana и 3 SDK-прогона проходят. Правила НУЦ, происхождение SDK, замена сертификата одной личности и независимое ревью ещё требуют подтверждения. Клод Opus 5.5/max не вернул ревью до таймаута.

НУЦ РК указывает, что для интеграции владелец информационной системы или законный представитель должен получить [комплект разработчика](https://pki.gov.kz/ru/developers/), содержащий библиотеки и тестовые сертификаты. Корректность реализации подписи и её проверки остаётся ответственностью владельца системы.

## Что сделать владельцу проекта

1. Получить согласованную текущую пару тестовых CRL. Формулировка для НУЦ: «SDK 2.0 и test.pki.gov.kz возвращают base CRL №166, delta CRL №2228 с BaseCRLNumber №167; требуется актуальная совместимая пара либо официальное разъяснение процедуры проверки». Для обращения достаточно номеров/версий и публичных URL; ключи и пароли не нужны. Затем сверить происхождение архива и актуальные правила проверки ЭЦП.
2. Уточнить у НУЦ, есть ли в комплекте **два подходящих тестовых сертификата на одну тестовую личность** для прогона замены без смены адреса; наличие `.p12` само по себе этого не доказывает. Отозванный комплектный сертификат уже найден и проверен отрицательным тестом.
3. Ручной NCALayer → detached-CMS точных байтов → серверная проверка цепочки/назначения/TEST OCSP и повтор квитанции уже пройдены на комплектном сертификате. Сохранить этот прогон как регрессию и повторить после подключения устойчивой идентичности; полная приёмка потребует замены сертификата и отказа старым доступам.
4. Отдельно определить законный источник актуальных полномочий представителя организации. Наличие действительного сертификата не заменяет такую проверку; до её появления корпоративный путь закрыт.

## Условие перехода к реальной ЭЦП-приёмке

Воспроизводимый прогон на ПК: NCALayer подписывает точные байты → сервер с официальным комплектом проверяет подпись и статус → новый сертификат той же тестовой личности сохраняет адрес → старый сертификат и ранее выданные разрешения отклоняются. При недоступности статуса сертификата операция не исполняется.

До выполнения этого условия можно разрабатывать контракт и unit-тесты, но нельзя маркировать их как работающую интеграцию НУЦ. Никакие реальные тенге или производственные ключи для этого этапа не нужны.
