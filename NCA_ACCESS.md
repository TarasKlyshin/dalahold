# НУЦ РК: доступ для технического прототипа

Статус на 30.09.2026: SDK 2.0 и комплектные тестовые ключи скачаны. [Локальный стенд](nca/README.md) реализует страницу NCALayer, API точных одноразовых распоряжений и Java-проверку CMS. В отдельном явном TEST OCSP-режиме пройдены SDK- и ручной браузерный сценарии «точные байты → NCALayer/CMS → строгая проверка ответа официального TEST OCSP → одноразовая HTTP-квитанция», затем повтор с той же сохранённой квитанцией без новой проверки статуса. Принятый сертификат совпадает с комплектным профилем «Сотрудник с правом подписи»; это не проверка корпоративных полномочий. **CRL-режим остаётся закрытым:** base CRL №166 меньше требуемого delta BaseCRLNumber №167. Автоматического перехода на OCSP нет. `authority/`, устойчивая идентичность, роли сделки, полномочия и кошелёк ещё не связаны; квитанция имеет только `scope: test_signature_only`.

Утилита OCSP SDK не устанавливает доверие к ответчику, соответствие CertID и свежесть; она не используется для приёмки. [Spike 012](.planning/spikes/012-strict-test-ocsp/README.md) реализует отдельную проверку доверенного ответчика, подписи, назначения, CertID, 32-байтового nonce и времени. Пройдены 47 синтетических/транспортных проверок и обязательные отрицательные проверки настоящих комплектных сертификатов: текущий `Физическое лицо/revoked` отклонён по проверенному TEST OCSP `revoked`, а `Казначейство клиент/valid` — до OCSP из-за отсутствия требуемого стендом назначения подписи. В обоих случаях квитанции и погашения запроса нет. На этапе Spike 012 проходили 88 Node + 7 offline Solana и 3 SDK-прогона; текущий набор указан ниже. Правила НУЦ, происхождение SDK, замена сертификата одной личности и независимое ревью ещё требуют подтверждения. Клод Opus 5.5/max не вернул ревью до таймаута.

Внутренний [Spike 014](.planning/spikes/014-personal-binding-intents/README.md): защищённая пара ключа отображения/SQLite, отдельные точные личные TEST-распоряжения регистрации и замены, атомарные эпоха/отказ старому сертификату/квитанция, резервное копирование и отказ при потере или смене ключа. Настоящая комплектная личная TEST-подпись регистрации, восстановление текущей копии и отрицательные случаи прошли; положительная замена личного сертификата пока только на тестовой модели. Сертификат с контекстом организации отклоняется даже при совпадении ИИН.

[Spike 015](.planning/spikes/015-retained-binding-checkpoint/README.md) добавляет обязательную удерживаемую локальную TEST-контрольную точку вне обычной копии ключа/БД. Она отклоняет старые копии и параллельные устаревшие реестры; новая запись и контрольная точка фиксируются/откатываются совместно. Потерянная точка не создаётся автоматически. Ключ защищён правами файлов владельца, не зашифрованным хранилищем; полный откат машины/тома с обеими БД, production-custody, физические сбои и публичная авторизация не приняты. [Процедура восстановления](nca/README.md) запрещает откатывать контрольную точку ради принятия старой копии.

[Spike 016](.planning/spikes/016-browser-personal-test/README.md) подключает отдельную страницу личной TEST-привязки с явным операторским opt-in, серверной сессией/CSRF и лимитами. Закрытая/истёкшая сессия не может записать привязку после ожидания SDK. Настоящая комплектная личная CMS через HTTP даёт одну TEST-квитанцию, повтор возвращает историческую; корпоративные/отозванные/неподходящие CMS и подмена байтов отклоняются. Последние code-тесты: 161 Node + 7 offline Solana и 4 SDK-прогона, без пропусков; код при фиксации ручной приёмки не менялся. [Ручная личная TEST-регистрация/повтор/закрытие](.planning/spikes/016-browser-personal-test/UAT.md) подтверждены пользователем. Независимый readback показывает одну привязку/квитанцию, отсутствие дубля и актуальную защищённую копию ревизии2; закрытие сессии опирается на ответ пользователя, не на БД. Agent browser QA остаётся заблокирован политикой службы; адаптивность/клавиатура/реальный cookie-отзыв требуют проверки. Это не вход с бизнес-доступом, кошелёк или полномочия.

[Восстановление после SIGBUS/WAL-index](.planning/spikes/016-browser-personal-test/RECOVERY.md) сохранило все строки старого стенда и первоначальную квитанцию; стенд переведён на rollback-журнал с FULL и отключённым mmap. Причина недоступности отображённой памяти ниже уровня SQLite не установлена. Проверка пароля/сертификата не является причиной этого сообщения о недоступном сервере.

НУЦ РК указывает, что для интеграции владелец информационной системы или законный представитель должен получить [комплект разработчика](https://pki.gov.kz/ru/developers/), содержащий библиотеки и тестовые сертификаты. Корректность реализации подписи и её проверки остаётся ответственностью владельца системы.

## Что сделать владельцу проекта

1. Получить согласованную текущую пару тестовых CRL. Формулировка для НУЦ: «SDK 2.0 и test.pki.gov.kz возвращают base CRL №166, delta CRL №2228 с BaseCRLNumber №167; требуется актуальная совместимая пара либо официальное разъяснение процедуры проверки». Для обращения достаточно номеров/версий и публичных URL; ключи и пароли не нужны. Затем сверить происхождение архива и актуальные правила проверки ЭЦП.
2. Получить **два действующих тестовых сертификата одного подходящего профиля на одну тестовую личность** для полного прогона замены без смены адреса. [Spike 013](.planning/spikes/013-test-subject-identity/README.md) подтвердил совпадение личности у действующих физлица и руководителя и раздельный ID организации, но это разные профили, не приёмка продления сотрудника. Сертификат «Сотрудник организации» в папке `valid` оказался отозванным по свежему TEST OCSP и правильно отклонён. Имена папок и наличие `.p12` не доказывают действительность.
3. Ручной NCALayer → detached-CMS точных байтов → серверная проверка цепочки/назначения/TEST OCSP и повтор квитанции уже пройдены на комплектном сертификате. Сохранить этот прогон как регрессию и повторить после подключения устойчивой идентичности; полная приёмка потребует замены сертификата и отказа старым доступам.
4. Отдельно определить законный источник актуальных полномочий представителя организации. Наличие действительного сертификата не заменяет такую проверку; до её появления корпоративный путь закрыт.

## Условие перехода к реальной ЭЦП-приёмке

Воспроизводимый прогон на ПК: NCALayer подписывает точные байты → сервер с официальным комплектом проверяет подпись и статус → новый сертификат той же тестовой личности сохраняет адрес → старый сертификат и ранее выданные разрешения отклоняются. При недоступности статуса сертификата операция не исполняется.

До выполнения этого условия можно разрабатывать контракт и unit-тесты, но нельзя маркировать их как работающую интеграцию НУЦ. Никакие реальные тенге или производственные ключи для этого этапа не нужны.
