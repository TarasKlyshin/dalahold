# DalaHold

Локальный TEST-прототип для агросделок в Казахстане: общие условия, версии документов, заявления участников и отдельные отзывы о покупателе и продавце.

[English](../README.md) · [Доказательства и ограничения](EVIDENCE.md) · [Недельный отчет и тексты ролика](updates/2026-10-11.md)

## Проблема и участники

Фермер и закупщик могут согласовывать условия в разных сообщениях и документах, а затем спорить о том, что принято или передано. Это **гипотеза для проверки с участниками**, а не подтвержденный результат исследования рынка.

DalaHold исследует общую версию сделки, явный источник каждого заявления и понятный путь приемки или спора. Действующий план начинает со сделки по КРС; молочный и зерновой сценарии остаются кандидатами для интервью.

## Что подтверждено

Снимок кода: `01139a9`, 4 октября 2026 года.

| Область | Подтвержденный уровень |
|---|---|
| Сделка | Анонимное unsigned TEST-демо воспроизводит принятую и спорную сделки через API: версии условий, обезличенные текстовые вложения и отзывы по ролям. |
| Экспорт | Реализованы полные пакеты материалов и офлайн-проверка согласованности. Хэш не доказывает автора, личность или физическую передачу товара. |
| ЭЦП НУЦ | Записаны подлинные проверки личного TEST-сертификата и ручная привязка одного человека через NCALayer. Настоящая подпись двух разных людей и успешная замена сертификата остаются открытыми. |
| Доступ и восстановление | Проверены отдельные локальные контуры доступа, повторов и копирования/восстановления unsigned-данных. Полная браузерная и production-приемка не подтверждены. |
| Solana | Реализована проверка devnet только чтением. Кошелек не настроен, подтвержденной транзакции нет, исполнение по умолчанию выключено. |
| Спрос | Есть карточки интервью и протокол теста. Подтвержденный спрос, пользователи и выручка не заявляются. |

Подписи двух участников, замена сертификата, полномочия бизнеса, хранение ключей и полный пользовательский сценарий еще требуют приемки. Реальные платежи, цифровой тенге и production-эскроу не входят в завершенный объем.

## Запуск unsigned-демо

Локальный запуск проверен с **Node.js v22.22.2** и встроенным SQLite. Для unsigned-демо не нужны npm-пакеты, SDK НУЦ, сертификаты и кошелек.

```sh
git clone https://github.com/TarasKlyshin/dalahold.git
cd dalahold
node web/participant-demo.mjs --port 0
```

Пока репозиторий приватный, необходим доступ к нему. Команда создает новый обезличенный пример, проверяет две выгрузки и закрывает свой сервер. Это подготовка через API; браузер и подписи не запускаются.

Команда выводит пути к `run-report.json`, `accepted-evidence.json` и `disputed-evidence.json`. Отдельная проверка выгрузки:

```sh
node web/verify-participant-evidence.mjs /path/to/accepted-evidence.json
```

Успех означает согласованность структуры. Файл `operator-access.json` содержит локальные коды доступа и остается приватным.

Для отдельного браузерного прогона при свободном локальном порте:

```sh
node web/participant-demo.mjs --serve
```

Откройте <http://127.0.0.1:4177/participants/> на том же компьютере. Создается новый unsigned-пример; сервер работает до Ctrl+C. Занятый порт вызывает отказ, существующие стенды и данные не заменяются. Реальную работу интерфейса проверяют отдельно по [протоколу UAT](../.planning/spikes/025-participant-runtime-ui/UAT.md). Подробности запуска — в [описании демо](../.planning/spikes/026-reproducible-demo/README.md).

## Проверки

В итоговом отчете по коду записаны **498 успешных Node-проверок**, **6 пропущенных opt-in SDK-групп** и **20 успешных офлайн-проверок Solana**. Подлинные SDK-прогоны записаны отдельно. Это не приемка браузера и не сертификация безопасности.

Команды полного набора приведены в [английском README](../README.md#verification). При оформлении документации повторно проверены запуск демо и обе выгрузки; весь тестовый набор заново не запускался. [Карта доказательств](EVIDENCE.md) показывает источник и границу каждого результата.

## Следующие шаги

1. Пройти браузерный сценарий: документы, экспорт, отзывы, спор, повтор и истечение сессии.
2. Подписать одну точную версию сделки личными TEST-ЭЦП двух разных людей.
3. Проверить подлинную замену сертификата того же человека с сохранением ID и отказом старому разрешению.
4. Провести 3–4 прогона с парами «фермер — покупатель». Предварительный порог продолжения: минимум 3 из 4 пар завершают сценарий за 10 минут, минимум две готовы к следующему тесту; иначе упростить или сузить процесс.
5. После проверки полномочий, безопасности, хранения тестового ключа и отдельного разрешения на исполнение — подтвердить одну devnet-транзакцию и подготовить материалы демонстрации.

Это последовательность из [плана реализации](../IMPLEMENTATION_PLAN.md) и [протокола пользовательского теста](../PROJECT_BRIEF.md). [Фокус на 5–11 октября](updates/2026-10-04.md) предложен по оставшимся пунктам; отдельный календарь не утвержден.
