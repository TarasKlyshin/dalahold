# DalaHold: контракт подключения НУЦ РК (подготовлено, не подключено)

Статус: **проект контракта и приёмки**. [Локальная тестовая страница/API/Java](nca/README.md) реализованы. В отдельном явном TEST OCSP-режиме проходят CMS из SDK, строгий статус и одноразовая HTTP-квитанция; CRL-режим всё ещё отвергает несовместимую пару (166 < 167), без автоматического fallback. Браузерное TLS-соединение NCALayer проверено, но его запрос подписи вернул неподдерживаемый ответ и пригодный CMS не получен. Идентичность, полномочия и независимое ревью не подключены. SDK-тестовая квитанция и Ed25519-фикстуры не являются приёмкой полной пользовательской интеграции НУЦ.

## Доверенная граница

Браузер отправляет только идентификатор выданного сервером challenge, подписанный контейнер и идентификатор сертификата в формате, подтверждённом SDK. Отдельные поля браузера (роль, сумма, получатель, версия условий, ИИН/БИН) не считаются подписанными. Сервер получает исходные байты challenge из собственной БД и проверяет, что подпись относится **именно к ним**, а не к повторно собранному «эквивалентному» JSON.

Для **тестового** прогона реализован detached-CMS: клиент получает base64 точных серверных байтов и вызывает [KNCA Basics](https://github.com/pkigovkz/sdkinfo/wiki/KNCA-Basics-Module) с `format: "cms"`, `signingParams: { decode: true, encapsulate: false, digested: false }` и явной тестовой цепочкой. Совместимость CMS-ответа установленного NCALayer ещё нужно подтвердить. Сервер проверяет единственного подписанта, назначение, закреплённую тестовую цепочку, время и выбранный источник статуса; пустой `chain` не используется. `statusSource` входит в подписываемое распоряжение: после смены режима старый неподписанный запрос отклоняется. Поля сертификата из ответа браузера игнорируются; сертификат извлекается из CMS и проверяется на сервере. Строгий OCSP-режим не выдаёт бизнес-разрешений.

Адаптер проверки должен вернуть только один из двух результатов:

- `verified`: проверенная подпись точных байтов; удостоверенная устойчивая идентичность субъекта; допустимое назначение сертификата; действующая доверенная цепочка; срок и статус сертификата на момент операции; идентификатор использованного сертификата. Сырые персональные поля и контейнер не уходят в Solana и не попадают в публичный журнал.
- `rejected`: любой дефект подписи, цепочки, назначения, срока, статуса, кодировки, неоднозначность субъекта либо недоступность проверки статуса. Никакое разрешение подписанту не выдаётся. Причина для внутренних тестов записывается без секретов; публичный ответ остаётся обобщённым.

Проверка корпоративного представительства **не является свойством сертификата**. После криптографической проверки отдельный источник должен подтвердить полномочия субъекта для организации и конкретного действия. Пока законный и проверяемый источник не выбран, этот путь закрыт.

## Что зафиксировать сразу после получения SDK

1. Версию SDK (локально: Java provider 0.7.8-current, util 0.8.5), официальные правила верификации, доступные тестовые сертификаты и требования к NCALayer на ПК; не помещать ключи и пароли в репозиторий, чат или записи тестов.
2. Согласованный формат challenge и точные байты, которые возвращает NCALayer: CMS/XML, encapsulated/detached, кодировка и поведение декодирования. Старые онлайн-примеры — ориентир, не доказательство совместимости с выданным комплектом.
3. Тестовый набор без секретов: хэш challenge, тип подписи, ожидаемое решение и обезличенный ID сертификата. Для успешного сценария нужны **две независимые стороны**; для смены доступа — новый сертификат той же личности; для отрицательного — отозванный/истёкший сертификат и недоступный статус.
4. Способ проверки актуального статуса (OCSP/CRL) и его таймаут/режим ошибки. `unknown`, timeout и недоступный источник трактуются как отказ, а не как `valid`.
5. Источник и срок актуальности корпоративных полномочий. Тестовый allowlist не должен быть помечен как гос-проверка.

## Приёмка адаптера

| Случай | Проверяемый результат |
|---|---|
| Точные серверные байты + действующая тестовая ЭЦП | `verified`, один определённый субъект, без выдачи контейнера или пароля в лог |
| Один изменённый байт, другая версия условий, сумма или получатель | `rejected` до создания одноразового разрешения |
| Повтор challenge или параллельная отправка | Одно погашение nonce и не более одного бизнес-результата |
| Отозванный/истёкший/неподходящий сертификат или недоступный статус | `rejected`, без движения состояния сделки или отправки транзакции |
| Сертификат действителен, полномочий организации нет | `rejected`, без обхода через поле роли из браузера |
| Новый сертификат того же проверенного владельца | Прежний `owner_id` и адрес; увеличен `auth_epoch`; старые доступы отклонены |
| Прямой вызов подписанта без свежего разрешения | Отказ, без универсальной операции подписи |

Источники для проверки актуальной процедуры: [НУЦ РК — разработчикам](https://pki.gov.kz/ru/developers/), [NCALayer](https://pki.gov.kz/ru/ncalayer/) и [официальные примеры НУЦ](https://github.com/pkigovkz/NCALayerJSExample). Фактические параметры вызовов и список проверок следует подтвердить по **выданной версии** SDK до реализации адаптера.
